# features

Проверки окружения для мониторинга. Каждая фича реализует общий интерфейс:

```kotlin
interface DataFeature<out T> { suspend fun getData(): T? }                                   // данные или null
interface ConditionFeature<in P> { suspend fun isMeetsCondition(input: P): ConditionResult } // проверка условия
```

`ConditionResult` — `True`, `False` или `Unknown(reason)`. Причина `Unknown` всегда из одного общего списка `UnknownReason`.

## Фичи

| Фича | Вход `isMeetsCondition` | `getData` | Время |
|---|---|---|---|
| `WifiNetworksFeature` | имена сетей (SSID) | сети из системного кеша | мгновенно, скан не запускает |
| `BluetoothConnectedDevicesFeature` | имена устройств | подключённые сейчас устройства | до 2 сек на профиль |
| `NearbyBluetoothDevicesFeature` | имена устройств | BLE-устройства рядом | скан до 10 сек, не чаще раза в 30 сек |
| `LocationFeature` | список `GeoZone` (точка + радиус) | нет | до 20 сек |
| `TimeFeature` | `TimePeriod` (начало и конец строками ISO 8601) | текущее время и его источник | мгновенно |

В фичах со списком на входе условие выполняется, если подходит **хотя бы одно** значение. Пустой список сразу даёт `False`, данные при этом не читаются.

`NearbyBluetoothDevicesFeature.getData()` сканирует без фильтра, а такой скан при выключенном экране ничего не получает. Поэтому в фоне он вернёт пустой список, хотя устройства рядом могут быть. Для фоновых проверок используйте `isMeetsCondition`: он сканирует с фильтром по именам и работает при выключенном экране.

## Разрешения

Объявлены в манифесте модуля и попадают в приложение при слиянии манифестов. Runtime-разрешения запрашивает приложение, сами фичи их не запрашивают: без разрешения фича отвечает `Unknown(PERMISSION_DENIED)`, а `getData()` возвращает `null`.

| Фича | Runtime-разрешения | Ещё нужно |
|---|---|---|
| `WifiNetworksFeature` | `ACCESS_FINE_LOCATION` | `ACCESS_WIFI_STATE` (выдаётся без запроса) |
| `BluetoothConnectedDevicesFeature` | `BLUETOOTH_CONNECT` | |
| `NearbyBluetoothDevicesFeature` | `BLUETOOTH_SCAN`, `ACCESS_FINE_LOCATION` | `BLUETOOTH_CONNECT` по желанию: без него имя берётся только из эфира |
| `LocationFeature` | `ACCESS_FINE_LOCATION` (запрашивается вместе с `ACCESS_COARSE_LOCATION`) | в фоне — foreground service типа `location` |
| `TimeFeature` | нет | |

Без геолокации `NearbyBluetoothDevicesFeature` не работает: `BLUETOOTH_SCAN` объявлен без флага `neverForLocation`, и без разрешения на геолокацию Android молча выбрасывает все результаты скана. `WifiNetworksFeature` дополнительно требует включённые Wi-Fi и геолокацию: без них Android отдаёт пустой кеш вместо ошибки, поэтому фича проверяет их сама.

## Причины `Unknown`

| `UnknownReason` | Когда | Фичи |
|---|---|---|
| `PERMISSION_DENIED` | не выдано runtime-разрешение | все, кроме Time |
| `SOURCE_DISABLED` | выключен Wi-Fi, Bluetooth, геолокация или сетевая геолокация | Wi-Fi, Bluetooth, Location |
| `SOURCE_UNAVAILABLE` | на устройстве нет нужного железа или сервиса, например сетевой геолокации | все, кроме Time |
| `TOO_FREQUENT` | предыдущий скан запущен меньше 30 сек назад | Nearby Bluetooth |
| `READ_FAILED` | система вернула ошибку при чтении или скане | Bluetooth |
| `NO_DATA` | данных нет: кеш Wi-Fi пуст, за 20 сек не пришло ни одной координаты | Wi-Fi, Location |
| `MOCK_DATA` | пришли только поддельные координаты (`isMock`) | Location |
| `NOT_ACCURATE_ENOUGH` | пользователь у границы зоны, погрешность не даёт решить | Location |
| `SOURCES_CONFLICT` | GPS и сеть показывают разные места, возможна подмена GPS | Location |
| `NOT_VERIFIED` | ответил только GPS, а сетевая точка не пришла за 20 сек; время выставлено вручную и нет сетевого и спутникового | Location, Time |

## LocationFeature

Одновременно слушает два независимых источника координат:

* **GPS** — спутники. Точный, но его можно заглушить или подменить.
* **Сеть** — местоположение по видимым Wi-Fi-точкам и сотовым вышкам. Грубее, глушилки GPS на него не действуют.

У каждой координаты есть погрешность. Android отдаёт её с уверенностью около 68%, поэтому мы умножаем её на 2 и получаем около 95%. Дальше `a` — это уже удвоенная погрешность. Для зоны с радиусом `r` и расстоянием до центра `d`:

* `d + a ≤ r` — точно внутри;
* `d − a > r` — точно снаружи;
* иначе — неясно.

Порядок проверки:

1. Зон нет → `False`. Нет разрешения → `PERMISSION_DENIED`. Геолокация выключена → `SOURCE_DISABLED`.
   Сетевая геолокация обязательна: одному GPS не доверяем, поэтому без неё GPS даже не включаем и сразу отвечаем:
   * на устройстве нет сетевой геолокации → `SOURCE_UNAVAILABLE`;
   * она выключена → `SOURCE_DISABLED`. На телефонах с Google её включает настройка «Точность определения местоположения Google».

   GPS недоступен или выключен → решаем по одной сети, не дожидаясь GPS.
2. Ждём координаты до 20 сек. Поддельные, старше 10 сек и без погрешности пропускаем.
3. Когда есть координаты от обоих источников, сверяем их. Они расходятся, если одна точно внутри зоны, а другая точно снаружи, или если расстояние между ними больше суммы их погрешностей плюс путь, который пользователь мог проехать между двумя замерами (до 30 м/с, около 108 км/ч):
   * расходятся 3 раза подряд → `SOURCES_CONFLICT`, стоп. Расхождение засчитывается заново, только когда обе точки новые, поэтому одна плохая точка не считается несколько раз;
   * расходятся, но реже → ждём следующий замер, первая точка GPS бывает плохой;
   * не расходятся и хотя бы одна точно внутри зоны или точно снаружи → `True` / `False`, стоп.
4. Прошло 20 сек без уверенного ответа:
   * последние координаты расходятся → `SOURCES_CONFLICT`;
   * есть обе, но обе «неясно» → `NOT_ACCURATE_ENOUGH`;
   * есть только сеть → её ответ, если он точный, иначе `NOT_ACCURATE_ENOUGH`;
   * есть только GPS → `NOT_VERIFIED`;
   * были только поддельные → `MOCK_DATA`;
   * ничего → `NO_DATA`.

Правила лежат в `LocationJudge` (чистый Kotlin) и покрыты тестами `LocationJudgeTest`.

`LocationFeature(context, trace = { line -> ... })` пишет в `trace` каждый шаг: какие источники доступны, какие включены, каждую пришедшую точку (погрешность, возраст, расстояние до зоны, принята или отброшена) и итог со временем. Подходит для логов и отладки.

В фоне фиче нужен foreground service типа `location`.

## TimeFeature

Берёт время из самого надёжного доступного источника, по очереди:

1. **Сетевое время** (NTP).
2. **Спутниковое время** (GPS).
3. **Системное время**, только если в настройках включено «Автоматически». Это уступка: пользователь может обойти и автоматическое время, но без неё фича часто не отдавала бы время совсем.

Сетевое и спутниковое время система запоминает при синхронизации и дальше отсчитывает по внутреннему таймеру, поэтому ручной перевод часов на них не влияет. После перезагрузки они недоступны до следующей синхронизации.

* `getData()` — время и источник (`NETWORK`, `GNSS`, `SYSTEM`) или `null`, если ни одному источнику нельзя доверять.
* `isMeetsCondition(period)` — текущее время внутри периода: от `start` включительно до `end` не включительно.

  ```kotlin
  timeFeature.isMeetsCondition(TimePeriod("2026-10-24T09:00:00+03:00", "2026-10-24T18:00:00+03:00"))
  ```

  Строки в формате ISO 8601 со смещением часового пояса: `+03:00`, `Z` для UTC, можно добавить пояс `[Europe/Moscow]`. Без смещения строка не принимается: непонятно, о каком поясе речь. Пояс телефона не используется.
* Время выставлено вручную, а сетевого и спутникового нет → `Unknown(NOT_VERIFIED)`.

Порядок источников лежит в `TrustedTimeResolver` и покрыт тестами `TrustedTimeResolverTest`.
